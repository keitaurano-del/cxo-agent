# タスク前進システム設計（MC-353 / 2026-08-01）

発端: Keita「タスクボードのタスクを進めるため（ブロックになっているところも含め）完了に向けて動けるような機能とか仕組み考えて」

## 1. 現状分析 — 未完8件のブロッカー内訳（2026-08-01時点）

| 型 | 該当タスク | 停滞の実態 |
|---|---|---|
| **A. Keita操作待ち** | MC-339(ExoClick再決済・7日) / MC-331(Redditスマホ登録・Show HN承認) | 決裁フローに載っても応答されないと無期限停滞。依頼がチャット/決裁/口頭に分散し「今なにを頼まれているか」の一覧がない |
| **B. 外部サービス制約** | MC-331(データセンターIP遮断) / MC-352(CAPTCHA) | 代替ルート（埋め込みブラウザ→Cowork→チャネル変更→保留）の試行が場当たり |
| **C. 共有ツリー衝突** | MC-290(31変更/51未追跡が3日横ばい) | 「誰の変更か」仕分けが行われずコミット保留が続く |
| **D. 拾われないTODO** | MC-334(テスト修理・1週間動きなし) | 担当割当てはあるが着手トリガーがない |
| **E. 大玉の継続** | MC-313/347/351 | 「次の一手」が行末尾の長文に埋もれ、外から進捗が見えない |

決裁フローの構造的ギャップ: pending の決裁は **Keita が decide する以外に閉じる手段がない**（例: GSC再同意の決裁は 7/31 に実対応済みなのに pending のまま残存＝ノイズ化）。

## 2. 仕組み（3層）

### 層1: 見える化 — ブロッカーレジストリ
- board-audit（毎日21:30）が未完タスクから `data/blockers.json` を生成:
  `{taskId, type(A-E), since, days, next_action, next_actor(keita|son|external), unblock_route}`
- Apollo タスクボード UI に「⛔ n日停滞・次の一手・待ち先」バッジを表示。
- 効果: 「何が・誰待ちで・何日止まっているか」が一目になる。

### 層2: Keitaアクションキュー「今日の2分」
- **Keitaにしかできない操作**（決済/承認/スマホ操作/アカウント認証）だけを1画面に集約するApolloカード。各項目 = 1タップ導線（決裁のdecideボタン or 外部リンク）＋所要時間表示。
- バラバラの依頼通知を廃止し、**夜1回のまとめ通知**（未処理がある日だけ）に一本化。
- 決裁フロー拡張:
  - `POST /api/decisions/:id/withdraw`（エージェントによる取り下げ・状況変化で不要になった決裁を掃除）
  - `expiresAt` と `fallbackOption`（期限までに未応答なら「この案で進める/保留する」を自動適用可能に。適用時は必ず通知）

### 層3: 自動前進エンジン（board-audit拡張）
- **エスカレーション規則**: 決裁未応答3日→まとめ通知で再掲(1回のみ) / 7日→縮退・代替案を自動起案してKeitaはボタン1つで確定（例: MC-339は「後回しに格下げ」案を既に提示済＝この規則の手動先行）。
- **停滞TODO自動ディスパッチ**: 動きX日なし かつ Son実装可能（コード/テスト系）なら、board-auditがsubagentへ自動委譲して即日消化（第1号=MC-334テスト修理）。
- **代替ルートプレイブック**(型B): 埋め込みブラウザ→Cowork→チャネル代替→保留 の順で試行し、結果をblockersに記録。同じ壁で二度悩まない。
- **共有ツリー仕分け**(型C): 日次で `git status` を作者・タスク別に仕分けし「今日コミット可能な塊」を提案（MC-290の解消手順そのもの）。

## 3. 実装フェーズ

| Phase | 内容 | 依存 |
|---|---|---|
| **P1（即日・UIなし）** | blockers.json 生成をboard-auditに組込・エスカレーション規則・MC-334自動ディスパッチ・夜まとめ通知1通化 | なし（cron/スクリプトのみ） |
| **P2** | Apollo UI: 「今日の2分」カード＋ボードの停滞バッジ | web build＋backend再起動（dev一声） |
| **P3** | decisions拡張: withdraw API・expiresAt/fallback | 同上 |

## 4. 効果の測り方
- 週次で「停滞日数の合計」「Keita待ち項目数」「自動消化件数」をboard-auditサマリに併記。減っていれば機能している。
